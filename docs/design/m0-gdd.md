版本：v0.2｜日期：2026-09-06｜用途：开发与验收第一个可玩版本。

状态：初始开发规格，尚未经过 Gameplay Playtest。本文中的数值、阵容、坐标和交互初值用于首版实现，不代表已验证的平衡结论。

Human Owner：本次需求发起人，承担本 Feature 的玩法确认；姓名待团队补录。Architecture Steward、Cocos & Platform Steward 的 Review 尚未完成。

## 1. 游戏定位与体验目标

一款以中国象棋走法为基础、采用敌方意图预告的单人回合制战术小游戏。玩家保护只能在出生区域内移动的主帅，操纵车外出杀敌、升级，在波次间购买队友，最终击杀第二波敌将。

视觉方向为《Into the Breach》式固定斜俯视的 2.5D 棋盘，棋盘与棋子均有立体厚度。M0 暂缓僵尸题材和像素角色，使用可辨识的象棋棋子模型作为 Placeholder。目标平台为微信小游戏，使用 Cocos Creator。

《陷阵之志》在本项目中的参考范围，是本次讨论确定的“先看到敌方意图，再用有限行动化解威胁”的体验。M0 不因此引入其其他系统。

玩家应在首轮试玩中体会到：

- 看清敌方下一步，靠移动、吃子、堵路、蹩马腿或改变炮架来解围。
- 在保护主帅与让车出击成长之间取舍。
- 通过一次购买，把新的象棋走法加入自己的解题工具。

首局目标时长暂定 5–10 分钟，不设置思考倒计时；是否达到目标由试玩记录验证。

## 2. 已确认范围与首版默认值

### 2.1 已确认的产品决定

- 完整 9×10 棋盘，保留中国象棋的走法语言。
- 初始己方阵容为一名主帅和一枚一级车，所有己方单位都由玩家直接控制。
- 主帅可移动，但只能在己方 3×3 九宫内活动；横竖相邻一步，也可沿九宫米字斜线走一步。
- 玩家阶段每枚己方单位各有一次行动；动作包含移动或攻击，不是先移动再额外攻击。
- 敌方提前预告，锁定目标位置，不随玩家移动而追踪目标。
- 执行时因阻挡、马腿、炮架等条件变化而失效的意图直接取消，不临时重新选招。
- 普通单位一击被吃；主帅和敌将拥有生命值。
- 车通过杀敌升级，一级、二级、三级分别最多攻击直线上的 1、2、3 个敌人。
- 贯穿遇到有血量的单位时造成 1 点伤害并停止，车留在本次行动起点；此前击杀保留。
- 两波战斗，每波斩将即结束该波，剩余敌军退场；第一波后购买，第二波后胜利。
- 己方主帅被将死或生命值归零时失败。
- 尸体、障碍地形与地形填充不进入 M0。

保留“车杀敌升级”。2026-09-06 修订以九宫与米字走法覆盖旧版四格限制，以立体象棋占位模型覆盖像素僵尸贴片要求。

M0 的升级只有车的贯穿数量提升；不增加攻击力、血量或行动次数。

## 3. 棋盘、坐标与单位

### 3.1 棋盘定义

- 棋盘有 9 列、10 行，共 90 个可占据位置；棋子放在线的交点上，本文“棋位”即一个可占据位置。
- 坐标为整数 `(x,y)`：`x=0..8` 从左到右，`y=0..9` 从己方底线到敌方底线。
- 河界位于 `y=4` 与 `y=5` 之间，作为象棋标识及兵卒过河判断，不阻挡车、马、炮。
- 每个棋位最多一个存活单位。阵亡单位立即移除，无尸体、掉落物或残留占位。
- 己方九宫：`x=3..5，y=0..2`，中心 `(4,1)`；主帅出生于 `(4,0)`。
- 敌方九宫：`x=3..5，y=7..9`，中心 `(4,8)`；敌将出生于 `(4,9)`。
- 用底色和米字斜线明确九宫。斜步只连接九宫中心与四角，每次移动一格，不可跨过中心一次走到对角。
- 此处允许帅/将斜走是本项目自定义规则，不是标准中国象棋的帅/将走法。M0 不执行将帅照面、长将、长捉或和棋规则。

### 3.2 棋种规则

| 棋种 | 阵营与生命值 | 移动及攻击 |
| --- | --- | --- |
| 帅 / 将 | 双方，己方 3 HP、敌方 2 HP | 自己九宫内横竖一步，或沿中心与四角连线斜走一步；目标为敌人则攻击，造成 1 点伤害 |
| 车 | 双方，1 HP | 横竖直线；普通移动不能跨越任何单位；己方车另有等级贯穿规则 |
| 马 | 双方，1 HP | 日字移动；对应正交相邻的马腿有任何单位时不可走；不能落在友军位置 |
| 炮 | 双方，1 HP | 移动时直线无阻挡；攻击时与目标之间必须恰好有一个任意阵营单位作炮架 |
| 卒 | 仅敌方，1 HP | 朝 `y` 减小方向前进一步；到达 `y≤4` 后还可横向一步，不能后退；攻击范围与移动一致 |

马、炮均可能作为商店队友。敌方单位不获得经验；敌方车固定一级。

### 3.3 通用动作与伤害

- 选择空位置执行移动；选择敌方位置执行攻击。一次成功动作消耗该单位本回合唯一行动。
- 非法指令不消耗行动；不能落在友军位置，也不能攻击友军。
- 普通目标受到一次攻击即移除，攻击者占据目标位置。
- 攻击主帅或敌将造成 1 点伤害，攻击者留在动作起点；即使本次伤害致死，也不前进。随后立即处理阵亡与胜负。
- 上述特殊受击规则按“主帅/敌将”身份判定，不按当前 HP 是否大于 1 判定；剩 1 HP 的敌将仍会阻止车贯穿。
- 玩家可让部分或全部单位不行动，直接结束回合；不累积未使用行动。
- 本玩家阶段内允许主帅暂时处于威胁中。单步操作不使用传统象棋的“不能送将”过滤，玩家可以通过后续队友行动完成解围。

### 3.4 车升级与贯穿

车个人累计击杀经验：每亲手击杀一个敌人获得 1 XP。友军击杀、只造成伤害、波次结束的敌军退场不计入车经验。

| 等级 | 累计 XP 门槛 | 单次最多接触敌人数 |
| --- | --- | --- |
| Lv.1 | 0 | 1 |
| Lv.2 | 2 | 2 |
| Lv.3 | 4 | 3 |

贯穿攻击执行顺序：

1. 玩家选中同一行或列上的一个敌方单位，作为本次攻击的最远目标；该方向到目标之间不能有友军，敌人数不能超过动作开始时的等级上限。
2. 沿直线由近到远结算，允许穿过敌人之间的空位。
3. 普通敌人直接被击杀。若一直到所选目标都是普通敌人，车最终停在所选目标原位置，不继续滑到目标后的空位。
4. 如先遇到主帅或敌将，对其造成 1 点伤害，立即停止整次攻击；车留在动作起点，已经击杀的单位不恢复。所选目标若在其后方，不会被击中。
5. 整次动作结束后统一增加经验、更新等级；新等级不扩大正在结算的攻击，也不返还行动。

空位移动仍遵守基础车规则，不能把“选空位”当成穿过敌人的方式。玩家执行前必须看到实际攻击路径、受害单位和最终落点预览。

例：三级车选择直线第三个小兵，沿途为“小兵 → 2 HP 敌将 → 小兵”。实际结果为第一个小兵消失、敌将剩 1 HP、第三个小兵不变，车仍在起点。

## 4. 回合与敌方意图

### 4.1 回合顺序

`生成敌方意图 → 玩家阶段 → 敌方按序执行 → 生成下一轮意图`。

进入波次后先生成并展示敌方意图，再交给玩家操作；敌方不会在玩家第一次行动前偷袭。

玩家阶段每枚存活己方单位各有一次行动机会，操作顺序自由。点击“结束回合”后锁定输入，敌方结算完成前不可再下令。全部棋子行动完也保留“结束回合”按钮，由玩家主动提交。

### 4.2 预告锁定内容

每个敌人每回合至多一条意图，包含行动者、起点、目标棋位、移动或攻击类型，以及公开的执行序号。意图不锁定受害者身份。

- 攻击目标位置上的己方单位换成另一枚己方单位后，新占位者可能受击。
- 玩家移动、吃子或升级后，原始意图不重选；界面更新的是该意图现在会成功、落空还是被取消。
- 敌方按波次配置中的固定顺序依次行动，界面显示 1、2、3 等编号。
- 每一步执行前，使用前面所有动作已经产生的实际棋盘检查是否合法。
- 行动者已经阵亡，则删除其待执行意图。
- 目的地被敌方自己的友军占据、车路被挡、马腿被堵、炮架数量不符时，取消该动作并留在原位。
- 一条移动意图若目标后来被占据，则取消，不临时改成攻击。

### 4.3 攻击落空的具体规则

攻击意图的目标位置变空后，按棋种处理，避免炮“无炮架移动却越过单位”的矛盾：

- 车、马、卒、将：若到原目标位置仍是合法的普通移动，就移动到那里，攻击落空；否则原地取消。
- 炮：仍按攻击规则检查炮架。炮架恰好一个而目标变空时，原地打空；炮架不再恰好一个时，原地取消。两者均不移动、不换目标。

以上规则同样用于界面预测、将死分析和实际结算，不能分别实现出三套不同结果。

### 4.4 M0 敌方决策

不制作通用象棋搜索 AI。每次生成意图时，各敌人基于同一个当前棋盘快照独立选择一条合法动作：

1. 优先攻击己方主帅；其次攻击己方车，再其次攻击其他队友。
2. 没有可攻击目标时，在合法空位移动中选择让自身到己方主帅的曼哈顿距离最小的目标。
3. 相同优先级按目标 `y`、再按 `x` 升序打破平局。
4. 没有合法动作则待机；不因为预计可能被玩家反杀而改变策略。

生成意图时不提前模拟其他敌人的未来移动，所以可能预告出目的地冲突。依照公开序号执行，后行动者届时失效就取消；UI 的结果预测应反映这一点。

确定性优先用于复现问题。敌方策略强度、首波节奏和解法丰富度均待试玩验证。

## 5. 将军、将死与结算

### 5.1 与血量及多人行动兼容的定义

本版采用自定义的“预告将死”，不是标准中国象棋的无血量将死，也不是搜索未来多回合的必败。

- **将军提示**：现在直接结束回合，按已公开意图和顺序结算，会使主帅受到至少 1 点伤害。
- **将死失败**：穷尽当前剩余己方行动的所有合法组合与顺序，既不能提前斩将结束当前波，也不能让主帅以至少 1 HP 存活于紧接着的敌方阶段之后。
- **被吃失败**：实际伤害结算使主帅 HP 降至 0。

例如，主帅有 3 HP，本回合必定受到 1 点伤害但仍能存活，不判将死，只提示危险。主帅没有安全落点，但车与马配合能清掉攻击者，也不判将死。

主帅被己方棋子围住、没有合法移动但未面临必死局面，不自动判负。没有可用操作时可以结束回合或重开；不添加回合上限或和棋系统。

### 5.2 判定时机与实现边界

- 玩家阶段开始，以及每次玩家动作结束后，更新威胁并分析剩余解围机会。
- 分析包含不行动、提前结束回合、所有可行动棋子的选择、目标与先后顺序，以及车升级后的后续局面。
- 至多 3 枚己方单位、每枚一次行动，使用有限深度枚举；搜索结束点调用与实际敌方阶段相同的纯逻辑结算。
- 找到任意存活方案或斩将方案就停止；只有完整证明不存在方案后才判将死。允许复用等价局面结果和分帧处理，不能把超时当作将死。
- 分析中阻止新指令写入同一局面，显示短暂“分析局势”；不得每帧无变化地重复计算。重开后旧分析结果必须失效。

这项定义是为衔接已确认的血量与回合制而给出的首版默认，需在试玩时由 Human Owner 重点检查。

### 5.3 终局优先级

每个原子动作结算后立即检查：主帅阵亡则失败；否则敌将阵亡则当前波胜利。波次已结束后停止所有剩余动作、意图和输入回调。

本版没有反伤或同时伤害，正常情况下不存在同一步双方将帅同时阵亡；防御性处理时以己方失败优先。

“将死”和“主帅阵亡”使用不同失败文案；二者都进入 Result，不能继续战斗。

## 6. 两波内容、商店与成长

### 6.1 固定初始配置

下表为首轮开发种子配置，不承诺已经可通关或已经平衡。开发 Agent 必须完成可通关验证，必要时仅调初始位置及数值，并回写修改与证据。

| 波次 | 单位 | 初始位置 | 敌方执行序号 |
| --- | --- | --- | --- |
| 第一波己方 | 主帅，3 HP | `(4,0)` | — |
| 第一波己方 | 车，Lv.1，0 XP | `(0,0)` | — |
| 第一波敌方 | 卒 | `(0,3)` | 1 |
| 第一波敌方 | 卒 | `(2,5)` | 2 |
| 第一波敌方 | 炮 | `(4,6)` | 3 |
| 第一波敌方 | 将，2 HP | `(4,9)` | 4 |
| 第二波敌方 | 卒 | `(4,4)` | 1 |
| 第二波敌方 | 马 | `(2,6)` | 2 |
| 第二波敌方 | 炮 | `(6,6)` | 3 |
| 第二波敌方 | 车，Lv.1 | `(0,7)` | 4 |
| 第二波敌方 | 将，2 HP | `(4,9)` | 5 |

第一波意图：学会选子、走车、看预告、保护主帅；至少存在能在首波升级到 Lv.2 的通关路径。第二波意图：使用新队友并体验升级车的多目标攻击；需要存在一条整局达到 Lv.3 的可选路径，但不要求每局都达成。

### 6.2 第一波结束与商店

1. 敌将 HP 归零，立即结束第一波，剩余敌人退场；退场不算击杀，也不发经验。
2. 玩家得到固定 2 金币，显示存活队伍、主帅剩余血量、车等级与 XP。
3. 商店固定出售马、炮，价格均为 2；买一枚后余额为 0，两张购买按钮禁用。
4. 马与炮不能升级。没有刷新、卖出、折扣、赊账、重复购买或主动治疗。
5. 玩家点击“进入第二波”。允许未购买直接继续；货币不足或重复点击购买不得产生单位或负余额。

### 6.3 跨波继承与部署

- 己方主帅保留当前 HP，不自动回复。
- 初始车若存活，保留 XP 与等级；若阵亡，不复活，也不能在 M0 商店补买车。
- 主帅回到 `(4,0)`，存活的初始车回到 `(0,0)`；购买的马部署到 `(2,0)`，购买的炮部署到 `(1,2)`。
- 不保留第一波的棋盘位置，不提供自由布阵界面。
- 清除上一波行动次数、选中目标、意图与提示，重新生成第二波敌人及意图；己方单位行动恢复可用。

### 6.4 结果与重开

第二波斩将后显示“胜利”。失败显示“主帅阵亡”或“将死，无可用解围方案”。结果页展示到达波次、回合数、总击杀与车最高等级。

“重新开始”回到第一波初始状态：主帅 3 HP、一级车 0 XP、金币 0、无购买队友。结果页和暂停菜单均可重开，无局外继承。

战斗中“暂停”冻结输入并显示继续、重新开始；进行重开时原子清理旧动作、动画回调和分析任务。切换前后台不能导致额外行动或重复发奖。不制作断线或关闭后的存档续局。

## 7. 表现、界面与操作

### 7.1 2.5D 立体象棋占位方向

- 固定正交斜俯视相机，具有水平偏转，画面同时看到棋盘顶面和两个侧面；棋盘包含厚底座与镶边，不能只是平面的二维矩形。
- 棋子采用真实 3D 圆盘占位模型，包含底座、侧壁、上沿与字面，使用受光材质呈现体积。禁止以僵尸图片或单张平面贴片代替本版棋子模型。玩法仍只使用二维棋位，不使用物理碰撞裁决走法。
- 固定相机，不提供旋转、自由缩放或拖动视角；棋位与触摸位置的映射应通过相机和棋盘平面计算。
- 己方偏朱红、敌方偏青灰，以阵营底座、符号和文字共同区分，不能只依赖颜色。
- 单位必须清晰显示“帅/将/车/马/炮/卒”、主帅或敌将血量；己方车显示等级及 XP。
- 用户已允许临时象棋模型，故立体几何棋子可作为本版交付；仍需标识为占位美术，不代表最终像素风或主题美术已经验收。
- 使用简单定向光、明暗材质与接触阴影占位，不要求骨骼、复杂阴影或血腥演出。保留短移动过渡、命中反馈、单位消失、升级提示。
- M0 暂无背景音乐与音效，不影响胜负信息可读性；音频属于后续待补资产，不创建通用音频框架。

### 7.2 手机布局

竖屏设计分辨率 720×1280，优先适配宽度，背景填充完整屏幕。HUD 和按钮使用安全区；棋盘在可用区域中等比缩放，必要时按剩余高度进一步收缩，不裁掉边线或主帅。

- 顶部：当前波次、回合、主帅 HP；暂停入口。
- 中部：完整棋盘、双方九宫及米字线、单位、敌方意图路径与序号。
- 底部：选中单位说明、车等级/经验、操作结果预览、“执行”和“结束回合”。

至少验证 9:16、9:19.5 和 3:4 三种视口，确认刘海与底部安全区不覆盖按钮。桌面鼠标与手机触摸共用同一条交互路径。

### 7.3 点选交互

1. 点己方尚未行动的单位，显示合法移动位置和可攻击目标。
2. 点目标，显示实际路径、伤害/击杀、动作后落点及对应敌方威胁变化预览。
3. 点“执行”提交动作；在确认前可换目标或取消选择，不消耗行动。
4. 已行动单位变暗并有明确标记；仍可查看说明，但不能再次提交动作。
5. “结束回合”可以在尚有未行动单位时使用，先显示一次确认提示；全部已行动则直接执行。

M0 不做行动撤销。动画播放和规则结算期间锁定重复提交；UI 动画完成与逻辑动作完成必须避免重复计数。

敌方箭头标出原始意图；失效意图用叉号/虚线标记，不擦掉历史预告。当前选中或全体顺序预览应反映前一个敌人移动后对后续炮架和阻挡的影响。

## 8. 给开发 Agent 的实现约束

### 8.1 工程边界

本节是 M0 交接建议，不是已经验证的全局架构或 ADR。优先遵守仓库 `AGENTS.md` 并复用执行时已经存在的能力。

- 执行前检查分支和用户未提交修改，使用 Feature Branch / Worktree，不直接在 `main` 开发。
- 首先读取 `docs/cocos/project-knowledge.md`、相关开发基线及 `docs/architecture/facts.md`；按任务使用 Gameplay、Scene/Prefab、微信本地构建技能。
- 若仍无 Cocos 工程，默认在仓库的 `game/` 子目录创建，避免对非空仓库根目录启用覆盖。若已有工程，复用它。
- 暂定本机已安装的 Creator 3.8.8；最终版本和真机兼容性需在实际构建中记录。
- 修改 Scene / Prefab 前明确本 Feature 的 Human Owner、检查所有可见 Branch / Worktree 的资产冲突；跨机器是否有人编辑同一资产仍由团队协调，不能凭本机检查宣称不存在。

### 8.2 最小规则与表现边界

规则用无 `cc`、无 `wx.*` 依赖的 TypeScript 实现，持有棋盘、单位、回合、意图、经济、经验与胜负。场景 Component 负责触摸、节点、动画和界面刷新，通过显式引用调用规则。

最低接口语义如下，名称可按实际项目风格调整，但不得遗漏行为：

| 输入或查询 | 输出及约束 |
| --- | --- |
| 查询单位合法动作 | 目标位置、动作类型、路径；不改变状态 |
| 预览动作 / 敌方顺序结算 | 伤害、击杀、终点、意图取消和终局预测；不发奖励或改真实状态 |
| 提交单位动作 | 检查阶段、单位与剩余行动后生成新状态及表现结果；非法输入无副作用 |
| 结束回合 | 按固定意图执行，处理终局；存活则生成下一回合 |
| 查询解围方案是否存在 | 考虑全部剩余己方行动及当前意图；不能污染真实 XP、金币或状态 |
| 购买 / 进入下一波 / 重开 | 只允许对应阶段操作，并按本文继承或重置状态 |

必要数据包括：棋位、单位唯一 ID、阵营、棋种、HP、等级、XP、是否已行动、当前阶段/波次/回合、金币、公开意图和终局原因。数值与波次初始配置集中到一个小配置模块，避免散落在场景回调中。

不增加全局 Singleton、Event Bus、ECS、通用 Manager/Service 集群、资源框架、对象池或存档系统。将死枚举复用相同规则函数；不用单独实现第二套简化战斗规则。

### 8.3 场景与状态

一个入口 Scene 足够承载 M0；Boot、战斗、商店与 Result 可以是同 Scene 中的状态及面板，不强制拆成多个 Scene。

逻辑流程：

`Boot → Start → Wave1 → Shop → Wave2 → Result → Restart`。

任意战斗阶段均可进入失败 Result。战斗内部包含意图准备、玩家操作、分析中、敌方结算；暂停为冻结交互的覆盖状态，不重建对局。

场景只需明确的 GameRoot、棋盘/单位表现根、相机和 Canvas/UIRoot。使用一个复用棋子 Prefab 承载单位表现与初始化参数，不把每条规则变成一个场景节点。

需报告每个 Component 的挂载节点、必填序列化引用、Prefab/材质/贴图引用和初始面板状态。脚本存在不等于完成场景组装。

### 8.4 Cocos MCP 使用路径与已知限制

v0.1 编写时仅检查过文件与源码。v0.2 修订时已有 `game/` 工程，使用 Creator 3.8.8；会话未直接暴露 Cocos 工具时，可通过仓库 `tools/cocos-call.mjs` 调用已配置的本地 MCP，再由 `tools/editor-bridge.mjs` 操作 Editor。已实际启动工程并预览本版立体棋盘。各项验收以测试记录为准，不将浏览器成功视为微信真机成功。

本版 `Main/GameRoot` 的 `M0Game` 保留棋盘根、单位根、相机、UI 根及棋子 Prefab 引用，新增必填 `chessMaterial`，通过 Editor Bridge 绑定内置 Standard Material 并保存。运行时复制该材质，避免仅凭 effect 名动态初始化而缺少预加载依赖。场景组装工具同步保留该绑定。

开发 Agent 应按以下顺序操作，并以其实际工具发现结果与参数 schema 为准：

1. 发现 Cocos MCP 工具，检查环境与工程；Windows 上显式传入真实 `creatorPath`。本机已存在路径为 `C:\ProgramData\cocos\editors\Creator\3.8.8\CocosCreator.exe`。
2. 新工程使用 3D 模板。已检查的本地源码中，`cocos_local_create_project` 接受的 3D 空模板名为 `empty`，不是 `empty-3d`。明确传 `createSkeleton:false`、`createScene:false`、`overwrite:false`，避免默认生成无关框架和 2D 场景。
3. 另用 `cocos_local_create_scene_from_template`，传 `template:"3d"` 创建入口场景；随后检查/安装 Editor Bridge，打开或复用正确工程并等待 Bridge 就绪。
4. 检查当前场景树和实际 Bridge 路由，再通过 Editor/Bridge 创建节点、挂载已导入组件、绑定资源并保存。不要手写 `.scene`、`.prefab`、`.meta` 或 UUID。
5. 用 `cocos_local_create_wechat_build_config` 写入入口 Scene、竖屏和明确设计分辨率；再使用 `cocos_local_build_wechatgame`、产物检查和运行证据能力完成本地验证。

**已发现的 Windows 适配风险：** 本地 MCP 源码的模板路径当前按 `dirname(dirname(creatorPath))/Resources/...` 拼接，且运行中 Creator 探测使用 `ps`。显式传入 Windows 路径并不足以保证这两项能力成功；自动创建工程默认分支还会生成 2D Scene。

如果模板或进程识别失败，先记录错误与真实安装目录。可使用实际可用的 Cocos Editor 功能创建 3D 工程，再通过已验证 Bridge 继续组装；不能伪造工具成功、无声切成 2D 网页或手写序列化资产绕过验证。没有可用编辑器控制能力时，继续完成可独立验证的逻辑，并准确列出待执行的 Editor 步骤，不宣称可玩版已完成。

MCP 本地源码位于被忽略的 `.tools/`，临时修补不能假定会自动同步到其他成员机器。需要长期修补时应沿仓库既有工具引导方式保存可复现变更。

微信开发者工具路径、项目 AppID 和三名成员的测试手机信息尚待实际环境确认。缺少这些信息不阻塞规则开发和 Cocos 预览，但不能据此完成真机验收；不使用占位 AppID 冒充真机成功。

技能中建议的通用脚手架服从本项目“只实现当前闭环”的护栏。项目配置、Scene、Prefab 和本地构建任务分别采用对应技能的检查要求，不照搬其默认 2D hierarchy 或整套 Manager。

## 9. 实施顺序与验收

### 9.1 实施顺序

1. 先完成棋盘和单位数据、基础走法、伤害、确定性意图与回合模拟，用测试锁定结果。
2. 加入车贯穿/升级、将死分析、两波转换、购买和完整重开；准备胜利与失败的可复现动作记录。
3. 使用 Cocos MCP/Editor 组装单 Scene，将点选、预告、执行、结束回合、商店与 Result 接上真实规则。
4. 完成竖屏适配、斜俯视厚棋盘与立体象棋占位模型及动作反馈，运行实际关卡试玩。
5. 本地构建微信包、检查产物、开发者工具验证、三台手机试玩；记录证据并提交必要 Steward Review。

不得把逻辑测试通过、脚本编译通过、场景装配完成、本地构建成功和手机运行成功混为同一完成状态。

### 9.2 必需规则测试

| 场景 | 期望 |
| --- | --- |
| 主帅越出九宫、跨两步或不沿米字线斜走 | 拒绝且不消耗行动；中心与四角间斜走一步合法 |
| 车走空位、普通吃子、友军挡路 | 分别正确移动、占领目标、拒绝 |
| 三级车连续三个普通敌人 | 击杀三个，停在所选第三目标位置 |
| 三级车遇“小兵—敌将—小兵” | 第一兵阵亡、将扣 1 HP、第三兵保留、车不动 |
| 一次攻击令 XP 越过升级阈值 | 动作结束后升级；本次攻击范围不变，不返还行动 |
| 车升级 | 仍只有 1 HP；不获得额外攻击力或额外行动 |
| 炮架数量为 0、1、2 | 只有恰好 1 个时可攻击；移动不能越过炮架 |
| 马腿被堵、卒过河 | 分别阻止相应马步、开放卒横向一步 |
| 敌车目标移空、换成另一己方单位 | 分别移到原预告位置、攻击新占位者 |
| 移走炮架、炮目标移空 | 分别原地取消、炮原地打空；均不追踪 |
| 后行动敌人的路径被前一个敌人改变 | 使用实际新棋盘取消或执行，与预览一致 |
| 主帅没安全落点，但队友能解围 | 不判将死 |
| 必须两枚队友按特定顺序配合才能解围 | 搜索能找到方案，不误判失败 |
| 主帅必受 1 点伤害但仍存活 | 仅将军提示，不判将死 |
| 先斩将即可免于致死的敌方阶段 | 不判将死，斩将后停止该波剩余行动 |
| 穷尽所有剩余动作均致死 | 判将死，停止输入，显示对应失败原因 |
| 模拟与分析反复运行 | 真实金币、XP、HP、回合与单位位置不变化 |
| 第一波斩将 | 仅一次奖励；剩余敌人退场不算击杀 |
| 购买连点、金币不足、跳过购买 | 不重复生成、不负余额、可正常进入第二波 |
| 跨波继承 | 主帅血量及存活车经验继承，死亡车不复活，位置按配置重置 |
| 分析/动画期间重开并等待旧回调结束 | 新局数据不受旧局回调污染 |

### 9.3 可执行 Playtest

用真实配置记录至少一条完整动作序列，包含第一波至少一次升级、一次购买、第二波斩将。马、炮两个购买分支均需验证可进入、可操作；至少各有一次正常通关试玩，不能只通过开发作弊跳过敌将。

单独使用测试局面验证炮架解围、马腿解围、多单位配合解围、将死与主帅实际阵亡；这些是规则验证夹具，不增加到正式关卡选择界面。

浏览器/Cocos 预览与微信运行检查：

- 冷启动可进入第一波，首次点选、目标确认、结束回合有效。
- 完整棋盘、活动区、血量、意图与按钮清晰可读；点选不会误落到相邻棋位。
- 胜利、阵亡、将死均有正确结果；连续重开三次不残留单位、监听、金币或动作。
- 暂停/继续及前后台切换不会让敌人多走、玩家重复行动或商店多扣钱。
- 记录最坏将死分析耗时与所用设备；目标是不出现肉眼可见的长时间卡顿。数值性能门槛待设备事实建立后再定，不将优化猜测写成项目规则。

### 9.4 M0 完成条件

- 规则测试与上述完整流程验收通过，有可回放的通关步骤或录像。
- 实际 Cocos 场景已保存，组件与资源引用有效，无关键运行错误。
- 本地微信小游戏构建和产物检查通过。
- 三名团队成员各在自己的手机上完成启动、操作、结果和重开，记录机型、系统、包版本及问题。
- Human Owner 完成玩法检查；Architecture Steward 与 Cocos & Platform Steward 完成对应 Review。
- 尚缺真机或 Review 时只能报告“开发阶段完成/待验收”，不能报告团队 M0 全部完成。

最终开发交付需要列出：修改文件、工程和 Scene 路径、组件/资源绑定、测试结果、可执行试玩步骤、构建产物、已验证设备与待办。素材缺口、MCP 限制和人工 Editor 步骤必须明确列出。
